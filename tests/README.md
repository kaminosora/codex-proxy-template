# 测试套件

这些脚本用来**验证这个工具真的做到了它声称的事**，以及在改动代码后确认没改坏。

```
cd C:\codex-proxy
.\codex-proxy.ps1 tests              # 跑全部
.\codex-proxy.ps1 test               # 只跑协议自测（最快）
pwsh -NoProfile -File tests\run-all.ps1 -SkipSlow    # 跳过耗时的
pwsh -NoProfile -File tests\run-all.ps1 -Only 01,08  # 只跑指定的
```

> 📌 **07 是交互式的**（按用户要求）：它要求你在**系统代理关闭**和**系统代理开启→Clash**
> 两种状态下各跑一遍，中途会停下等你把系统代理改好并回车确认。
> 跑法、判读标准、以及"为什么要两遍"见
> [修复与验收备忘.md](../修复与验收备忘.md#i-07-改成交互式双跑按用户要求)。
> 只想快速跑一轮的话：`pwsh -NoProfile -File tests\07-egress-paths.ps1 -Only C`

> ℹ️ `run-all.ps1` 会在跑之前**自动拉起守护进程**（02/07/08 需要它）。
> 因为 06 号套件跑完会把守护进程停掉，不自动拉起来的话紧随的 07 必然失败。

> ⚠️ 部分脚本会**起停守护进程**（06）或**反复重启 Codex**（07）。
> 跑完请执行 `.\codex-proxy.ps1 app` 恢复使用。

## 影响范围（跑之前先看这个）

| 级别 | 脚本 | 会不会影响你正在用的服务 |
|---|---|---|
| 🟢 **完全安全** | `01`、`02`、`08`、`09` | **不会**。01/02 只用临时端口和只读 HTTPS 请求；08 只读查询桌面进程；09 只 ssh 查询服务器。守护进程和 Codex 都不受影响，可以随时跑 |
| 🟢 **完全安全** | `04`、`05` | **不会**。04 起一个**独立** mihomo（随机端口、独立数据目录）；05 只起自己的测试进程。两者都不碰 17890~17893，也不碰 Clash Party |
| 🟡 **基本安全** | `03` | 同样起独立 mihomo，但会**读取** Clash Party 的订阅文件做只读比对。实测 Clash Party 的文件零改动 |
| 🟠 **有副作用** | `05` | **会打断部分出口**。它需要让进程占住 17891/17893 来验证"端口反查回收"，而 `reapPreviousChildren` 会忠实地把占这些端口的进程当孤儿清掉——**包括正在运行的守护进程的 xray / 回落 mihomo 子进程**。跑完 `status` 会看到 `xray:jp` / `clash-party` 变 DOWN，**这是预期现象**。恢复：`.\codex-proxy.ps1 restart`；想完全避免：先 `.\codex-proxy.ps1 stop` 再跑，跑完 `start` |
| 🔴 **会打断服务** | `06` | **会**。它要反复 `start` / `stop` / 强杀守护进程来审计生命周期。**跑的期间专用代理会中断** |
| 🔴 **会打断服务** | `07` | **会**。它要反复关闭并重启 Codex 五次。**跑的期间 Codex 会被关掉** |

**结论**：

- 想体检又不想被打断 → 只跑绿灯的：`pwsh -NoProfile -File tests\run-all.ps1 -Only 01,02,04,05,08,09`
- 红灯的两个是"要复现问题才跑"的工具，别在日常使用中途跑。

**所有脚本都不会**：修改系统代理、写注册表、改 Clash Party 配置、装服务、改 Codex 的 `config.toml`。
`06` 改动的只有本项目 `run\` 里的状态文件和 17890~17893 四个端口。

### 01 与 02 的分工

两者都验证"代理能用"，但层次不同：

| | 01 | 02 |
|---|---|---|
| 目标 | 桥接**协议本身**正确 | 整条**通道**能通到 OpenAI |
| 网络 | **完全不碰真网络**（本地假目标 + 假出口） | 真实访问 `auth.openai.com` / `chatgpt.com` |
| 能查出 | 分片丢字节、握手解析错位、pause 死锁 | DNS 是否远端解析、并发是否串线、HTTP 层是否通 |
| 出问题时说明 | 代码写错了 | 出口或网络有问题 |

`check` 命令只验证出口 IP 和 TCP 连通性，**不验证 HTTP 层**——`02` 补的正是这一层。

**关键设计**：两个保险必须**各自独立可验证**，否则"一个生效"会掩盖"另一个失效"：

| 保险 | 触发条件 | 测试怎么保证它独立 |
|---|---|---|
| 保险 1：读 `children.json` 的 `pids` | 守护进程被强杀前记录过子进程 | 孤儿 A 用**随机端口**，不在 17891/17892/17893 清扫列表里 → 只能靠读 `pids` 清掉 |
| 保险 2：按端口反查 | 强杀来不及记录任何东西 | 孤儿 B 占 17893，但 `children.json` 里**不记它** → 只能靠端口反查清掉 |

> ⚠️ `children.json` 的格式是 `{ daemon: <pid>, pids: [pid, ...] }`（见 `recordChildren()`）。
> 早期测试写成了 `[{name,pid,port}]`，导致保险 1 空转而测试**看起来**通过——这个坑记在下面的历史里。
>
> ⚠️ **副作用**：日志里那两行 `已清理上一轮残留的子进程` 里包含**守护进程自己的 xray / mihomo 子进程**
> （它们当时正占着 17891/17893）。所以跑完 `status` 会看到 `xray:jp` / `clash-party` 变 DOWN，
> **这是功能正常工作的表现，不是故障**。恢复：`.\codex-proxy.ps1 restart`。
>
> **阈值为什么不卡在 8 秒**：每次 `killTree` 成功前会依次尝试 `taskkill` → `Stop-Process` → WMI，
> 每层各等超时；本测试共 6 次回收，实测累计约 14 秒属正常。定 40 秒是为了验证"没有无限挂住"，
> 而不是卡性能——早期定 8 秒就误报了。

### 07 — 三路径对照实验

**这个测试建议在两种系统代理状态下各跑一次**，因为 A / B 两轮的结论不同，
而 C / D / E 三轮与系统代理状态无关（两次应完全一致）。

**本脚本不修改系统代理**，只在开头读取并打印当前值。

#### 状态一：系统代理【关闭】（Clash 客户端可以没开）

| 轮次 | 配置 | 实测 |
|---|---|---|
| **A** | 直连（无参数、无环境变量） | **直连外网 46 条**，走代理 0 条，体积 15 MB（只有壳） |
| **B** | `--proxy-server` 指向 Clash 7890 | **0 条连接**（7890 没人监听） |
| **C** | `--proxy-server` 指向我们的 17890 | **我们的 298 条**，直连 0，走 Clash 0，体积 93 MB（完整界面） |
| **D** | `--proxy-server` 指向死端口 17899 | **0 条连接**（代理不可用 → 停在登录页） |
| **E** | 无参数 + 环境变量指向我们的 | **直连外网 48 条**，走代理 0 条 |

#### 状态二：系统代理【开启 → Clash 7890】，且我们的代理也在跑

| 轮次 | 配置 | 实测（2026-10-10 实跑） |
|---|---|---|
| **A** | 直连（无参数、无环境变量） | **Clash 37 条**，体积 **96.2 MB（进了主界面）** —— 不给参数时它**读系统代理并成功用它** |
| **B** | `--proxy-server` 指向 Clash 7890 | **Clash 33 条**，体积 19.3 MB（停在登录页） |
| **C** | `--proxy-server` 指向我们的 17890 | **我们的 29 条**，直连 0，走 Clash 0，体积 47.6 MB |
| **D** | `--proxy-server` 指向死端口 17899 | **0 条连接**，体积 11.5 MB |
| **E** | 无参数 + 环境变量指向我们的 | **Clash 17 条**，体积 26.9 MB（走的是系统代理，不是我们的） |

**两次对比得出的结论**：

| 结论 | 由哪两轮对照得出 |
|---|---|
| **不给参数时 Codex 读系统代理** | A 轮：系统代理关 → 直连；系统代理开 → 全部走 Clash |
| **给了 `--proxy-server` 就只认它** | C 轮两次都是"全部走我们、零直连、零走 Clash"，与系统代理状态无关 |
| **代理不可用 → 零连接** | D 轮两次都是 0 条 |
| **Chromium 不采纳环境变量** | E 轮：指定了 `HTTP(S)_PROXY=17890` 却一条都没走我们（系统代理关时直连、开时走 Clash） |

> ⚠️ **A 与 B 的体积差异（96.2 MB vs 19.3 MB）说明"走通了代理"≠"界面一定加载完成"**。
> 两者都走 Clash 7890，但只有 A 进了主界面。可能是 Clash 里 OpenAI 相关规则/节点的通断、
> 或站点资源缓存命中的差异。**这不是本工具的问题**（两轮都没走我们的代理），
> 但说明单看"连接数"不足以判断应用是否可用——**配合 `user-data-dir` 体积一起看才准**。
>
> ⚠️ **C 轮必须先确认 17890 在监听**。实测踩过一次：忘了 `start` 就跑，C 轮退化成"测死端口"，
> 得到"零连接"的假结论。脚本已加前置校验，未监听时会直接拒绝并提示。

**体积判读法**：`user-data-dir` 超过 50 MB = 界面资源加载成功（进了主界面）；10~30 MB = 只有壳（停在登录页）。

### 源码重建过程中重新暴露的问题（2026-10-11）

> 背景：`codex-proxy.mjs` 曾被 `Set-Content -NoNewline` 意外压平（换行全丢），
> 从会话日志恢复到 10/9 的基线后逐项重做功能，期间这些**基线自带的 bug** 再次暴露并被修掉。
> 它们都在 `14-yaml-typing.mjs` / `13-uplink-accounting.mjs` 里被固化成了断言。

| 问题 | 症状 | 修复 |
|---|---|---|
| **SOCKS5 问候语长度写死 2 字节** | 客户端常把「问候 `05 01 00`」和「请求」**合在一个 TCP 段**发出。写死剥掉 2 字节会留下一个孤立的 METHOD 字节，后续字段整体错位 → 解析出 `bad atyp` → 回 `05 01`（general failure），表现为**握手莫名失败** | 按 `NMETHODS` 剥掉 `2 + buf[1]` 字节；问候没收全时先等齐再继续 |
| **`socksConnect` 要求回复 10 字节** | RFC 1928 的 `BND.ADDR/BND.PORT` 客户端**根本不需要**，实践中常见只回 4 字节的实现。写死长度会让这类出口**永远握手不上**（报 `socks timeout`） | 拿到 4 字节且 `REP=0`、`ATYP` 合法即判定成功，不等 BND 部分 |
| **订阅解析器只认块式 YAML** | Clash Party 订阅用**流式**写法 `- { name: '…', type: ss, … }`。旧解析器把每行当成"只有一个键、值是 `{…}`"丢弃 → **55 个节点全变空对象** → `nodes` 报"没有可用节点" | 增加流式解析：按**顶层逗号**切分（跟踪引号与 `{}` 嵌套），按**第一个顶层冒号**切键值。节点名里的冒号逗号（`'官网: www.雨燕云.com'`）不会被切坏 |
| **`yamlScalar` 一律加引号** | 解析出来的值都是字符串，但 YAML 有类型：`udp: 'true'` → mihomo 报 `expected type 'bool', got unconvertible type 'string'`；`ech-opts: '{…}'` → `expected a map, got 'string'`。**回落出口 / `node-test` 的内核直接启动失败** | 按类型输出：布尔裸 `true`/`false`、纯数字裸输出、流式 map/数组原样输出；只有真正需要引号的（首尾空白、含 `:` `#` `\|` 等指示符、像 `null` 字面量）才加引号 |
| **块式解析没把 port 转成数字** | mihomo 要求 `port` 是数字，字符串会拒绝 | 抽出 `setParsedKey()`，块式与流式共用同一套类型规则 |
| **`coreExe()` 候选里没有我们自己的副本** | 会直接用 Clash Party 的 `mihomo.exe` → 触发它的"高权限内核"检测弹窗（**选取消 = Clash Party 退出**） | 候选顺序改成：显式配置 → `bin\codex-core.exe`（首选）→ Clash Party 自带（并打印警告说明风险） |
| **回落配置的 `proxies` 段是裸 JSON（假测试掩盖了它）** | `buildConfig()` 用 `nodes.map((n) => JSON.stringify(n))` 拼节点行，输出既没有 YAML 列表项的 `- ` 前缀、又是 JSON 格式：<br>`proxies:`<br>`{"name":"🇯🇵 日本1","type":"anytls",…}`<br>→ mihomo 报 `yaml: line 24: could not find expected ':'` → **`clash-party` 出口完全起不来**，`status` 里那一行直接消失。用户实测才发现（`node-test` 走的是另一条生成路径，已修好，所以只有回落出口坏 —— 更容易漏掉） | 抽出 `nodeToYaml(n)` 输出 `  - { name: …, k: v, … }`（走 `yamlScalar` 保证类型正确）；并**修掉掩盖它的假测试**（见上节） |
| **`app` 命令每次都杀重启 Codex** | 无脑"杀掉再拉起"，**打断你正在编辑的内容** | 加 `codexUsingOurProxy()`：先看主进程命令行有没有 `--proxy-server=127.0.0.1:<我们的端口>`，再看有没有连到我们端口的已建立连接；在用就跳过（`app --force` 可强制重启） |
| **`start` 打印过期的出口名（如"出口 = dead"）** | `cmdStart` 轮询时读到的是**上一轮遗留的 `state.json`**（新守护进程还在初始化、没写状态），于是把上次的出口名（`dead` 是测试用的假出口）当成这次的 | ①spawn 前先删掉旧 `state.json`；②校验 `state.json` 里的 `startedAt` 必须 ≥ 本次启动时间，否则不采信 |
| **xray 的 REALITY 公钥字段名只认一个** | 配置里字段叫 `password`（Xray 26.x 的命名），代码却只读 `publicKey` → 生成的 `realitySettings` 里公钥为空 → 内核直接退出 `code 23`：`Failed to build REALITY config. > infra/conf: empty "password"`。**xray 出口整个用不了** | 三个字段名都读（`password` / `publicKey` / `public_key`），生成配置时**两个键名都写**（多余的会被忽略）；并加 `validateConfig()` 在启动前给出清晰提示，而不是让人去翻 `xray-client.log` |
| **`cmdStart` 不检查监听端口** | 端口被上一轮孤儿占着时照常 spawn，守护进程绑不上就退出（日志里仅一句 `EADDRINUSE`），而命令只报"启动失败"，看不出原因 | 启动前先查端口占用：有占用且 pid 文件说没在跑 → 判为残留并清理 + 等端口释放；同时给 `Bridge.listen` 加**递增间隔重试**（8 次，最多约 10 秒），吃掉"刚回收完还没退干净"的竞争窗口 |
| **`pidListeningOn` 在受限环境会假报"空闲"** | 沙箱里 `spawnSync netstat` 直接 `EPERM`，返回空 → 函数返回 null → `status` 把被占的端口显示成"无监听"，**看起来端口是空的**（实测踩过：孤儿占着 17890，status 却说无监听） | ①识别 `out.error`，打日志说明"查不到 ≠ 空闲"；②`status` 先用 `canLookupPorts()` 判断能否查询，查不到就只打印一句"本环境禁止查询端口归属"，**不再逐端口显示"无监听"**（那会误导） |
| **`auto` 解除后 `status` 仍显示"已强制指定"** | `release-pin` 只改了内存里的 `pinnedUplink`，没落盘；要等最长 5 秒的定时 `writeState()` 才刷新，看起来像 `auto` 没生效 | 解除后立刻 `writeState()` |

### ⚠️ 假测试（复刻生产逻辑，测的是复制品）

> 这是最危险的一类问题：**测试是绿的，生产代码却是坏的** —— 因为测试没有调用生产代码，
> 而是自己复刻了一份"看起来等价"的实现。它在被测代码坏掉时不会失败，于是给人一种虚假的安全感。

| 位置 | 假在哪 | 后果 | 修复 |
|---|---|---|---|
| **`03-fallback-isolation.mjs` 自己拼回落配置** | 第 114 行用 `Object.entries(p).map(...yamlScalar...)` **手写**了节点行，而不是调用生产的 `ClashPartyUplink.buildConfig()`。讽刺的是手写的那份**格式是对的**（`  - { … }`），所以内核起得来、测试全绿 | 生产的 `buildConfig()` 当时输出的是**裸 JSON 且没有 `- ` 前缀**：<br>`proxies:`<br>`{"name":"…","type":"anytls",…}`<br>→ mihomo 报 `yaml: line 24: could not find expected ':'` 退出 → **`clash-party` 出口整个起不来、`status` 里那一行直接消失**，而测试一直是 PASS。用户实测才发现 | ①`03` 改成调用生产 `buildConfig()`，并加**结构性断言**（`proxies` 段每行必须是 `- { … }`）；②再加一道**内核校验**：`mihomo -t -f <生成的配置>`，让内核自己说行不行（比任何自定义断言都可靠）。两条都会捕获这个 bug |
| `11-probe-overhead.mjs` 第 7 步读源码文本 | 用 `src.includes('requestTiming')` 这类**字符串匹配**断言"探测是轻量的" —— 它只检查代码里出现了某个词，不检查行为 | 代码用错了参数（比如不是 `maxBytes: 1` 而是下载 256KB）它也照样 PASS | 改成断言 `maxBytes: 1` 确实存在、且不含 `dlBytes`/`262144`；并把"读函数体"的范围界定修对（早期用 `selectUplink` 当终点，而它在目标函数**之前**，导致截取一路到文件末尾、把别处的 `dlBytes` 也算进来） |

**教训**：测试要**调用**生产代码，不要**重写**它。一旦发现测试里出现了和生产同构的循环/格式化逻辑，那基本就是假测试。
